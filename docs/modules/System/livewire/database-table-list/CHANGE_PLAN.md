# CHANGE PLAN — Add Import Table to System / Database / TableList

## Goal

Add a safe **Import Table** capability next to the existing per-table Export/Restore actions in `System / Database / TableList`.

This is a feature change, not only a refactor, so it is documented separately from `REFACTOR_PLAN.md`.

## Intended User Flow

For each non-protected table row:

```text
Export SQL
Import SQL
Restore existing backup
Truncate
Drop
```

Recommended Import Table flow:

```text
Click Import
    ↓
Open modal for the selected table
    ↓
Choose one .sql file
    ↓
Validate file + target table
    ↓
Create safety backup of current target table
    ↓
Import SQL into the target table
    ↓
Refresh table metadata
    ↓
Success / safe failure message
```

## Scope

Expected files after approval:

```text
Modules/System/Livewire/Database/TableList.php
Modules/System/resources/views/livewire/database/table-list.blade.php
Modules/System/Services/DatabaseService.php
```

Targeted tests/documentation may also change.

No database migration is required.

---

## Livewire State

Add only the UI state needed for table import, for example:

```text
showImportModal
importTargetTable
importFile
isImporting
```

Use Livewire upload support for the temporary SQL upload.

Do not persist arbitrary browser file paths.

## Authorization

Importing SQL mutates database data and therefore must require:

```text
database.restore
```

The permission check must run inside the Livewire import/open action, not only at route/page level.

## Protected Tables

Recommended default for this feature:

- **Do not allow manual Import Table for protected tables** (`users`, `migrations`, permissions/roles, etc.).
- Existing full-database restore behavior remains unchanged.

Reason: a single-table browser upload is easier to misuse and does not have the same full-database recovery context.

If protected-table import is ever required, it should be separately approved with stronger safeguards.

---

## Accepted File

Initial version should accept only:

```text
.sql
```

Recommended constraints:

- validate extension and MIME/file readability as far as practical;
- enforce a configurable/max upload size appropriate for PHP/Livewire limits;
- never trust the original filename as a filesystem path;
- store temporary/import files privately;
- delete temporary files after success/failure.

## SQL Contract

Import Table should target exactly one selected table.

Recommended accepted dump format:

- SQL generated by this System module's per-table Export (`mysqldump <database> <table>`), or compatible single-table MySQL/MariaDB dump;
- the dump must reference the same selected table;
- reject obvious multi-table/full-database dumps for this action.

The browser cannot choose a different target by modifying SQL metadata without service validation.

## Service Responsibilities

Add a dedicated service workflow, conceptually:

```text
importTableFromFile(targetTable, uploadedSqlPath)
```

The Service must own:

1. validate target table identifier and current existence;
2. reject protected target tables;
3. inspect/validate the SQL dump as a single-table dump for the target table;
4. create a safety backup of the current target table;
5. import SQL using streamed process input;
6. on failure, attempt to restore the safety backup;
7. log technical diagnostics server-side;
8. return a stable result / throw user-safe domain exception;
9. clean temporary uploaded SQL according to lifecycle rules.

Livewire must not parse or execute SQL itself.

---

## Data Integrity Strategy

Before table import:

```text
Current target table
       ↓
Safety backup
       ↓
Import uploaded SQL
```

If import fails:

```text
Import failure
      ↓
Attempt automatic restore from safety backup
      ↓
Report success/failure safely
```

Because MySQL DDL/import is not fully transactional, the safety backup/recovery path is required.

## Concurrency

Use a per-table import lock or equivalent guard so two imports/restores cannot mutate the same table concurrently.

At minimum:

```text
same table import/restore
→ only one active operation
```

Full database restore should also remain protected by its existing global restore lock.

## UI / UX

Recommended per-row action:

```text
Import
```

Click opens a modal showing:

- target table name (read-only);
- `.sql` file selector;
- warning that current table data can be replaced;
- note that a safety backup will be created automatically;
- Cancel;
- Import button.

While importing:

- disable modal close/actions;
- use truthful indeterminate loading state;
- do not display fake percentage;
- prevent double submission.

After success:

- close modal;
- clear upload state;
- refresh table row metadata;
- notify success.

## Error Handling

Do not display raw process/SQL/storage exception messages.

UI should use stable messages such as:

```text
File SQL không hợp lệ cho bảng đã chọn.
Import bảng thất bại. Dữ liệu cũ đã được phục hồi.
Import bảng thất bại và cần kiểm tra phục hồi trong log.
```

Technical details go to server logs/audit.

## Tests / Verification

Recommended focused coverage:

```text
[ ] unauthorized user cannot import
[ ] protected table import is rejected
[ ] invalid table identifier is rejected
[ ] non-SQL upload is rejected
[ ] multi-table/full dump is rejected
[ ] dump for another table is rejected
[ ] valid exported single-table SQL is accepted
[ ] safety backup is created before import
[ ] failed import triggers recovery attempt
[ ] concurrent import of same table is blocked
[ ] temporary upload is cleaned up
[ ] user-facing errors do not leak process internals
```

Manual test in non-production:

1. export a test table;
2. modify table data;
3. import the exported SQL;
4. verify schema/data restored as intended;
5. test invalid SQL and recovery path.
