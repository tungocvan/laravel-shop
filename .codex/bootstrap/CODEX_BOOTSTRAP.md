# Codex Bootstrap

This document is the operating contract for AI-assisted development in this Laravel workspace. Read it before analysis, refactoring, rebuilding, or file generation.

## Laravel 12 Conventions

- Target Laravel 12 on PHP 8.3, using the framework conventions already present in the repository.
- Keep application code PSR-4 autoloadable through `App\` and `Modules\`.
- Prefer constructor injection and Laravel container resolution over static service creation.
- Use Laravel validation, authorization, policies, gates, events, jobs, queues, storage, cache, and logging instead of custom infrastructure.
- Use Eloquent relationships, casts, accessors, scopes, factories, seeders, and migrations idiomatically.
- Keep controllers thin: HTTP validation, authorization, orchestration, redirects, and responses only.
- Put domain behavior in module services, actions, DTOs, policies, jobs, events, observers, or models according to existing module patterns.
- Run formatting with Laravel Pint when PHP code changes.

## Livewire 3 Conventions

- Livewire components live under `Modules/<ModuleName>/Livewire`.
- Component aliases are generated by `Modules\ModuleServiceProvider` as `<lower-module>.<kebab.path>`.
- Component views should live under the module view tree, normally `Modules/<ModuleName>/resources/views/livewire/...`.
- Use typed public properties where practical.
- Validate every external input with `rules()`, attributes, Form objects, DTOs, or explicit `$this->validate()`.
- Authorize mutating actions inside the Livewire method, not only in Blade.
- Use pagination for lists and avoid unbounded `get()` calls.
- Keep Livewire components focused on UI state and user interaction. Move data access and business rules into services.
- Use events intentionally and document event names when they cross component boundaries.

## Service Layer Architecture

- Each module should expose a small set of services under `Modules/<ModuleName>/Services`.
- Services own business workflows, transactions, import/export orchestration, and reusable queries.
- Services should receive dependencies through constructors where possible.
- Services may return Eloquent models, collections, DTOs, arrays, export files, or operation result objects, but the return shape must be explicit and documented.
- Put database writes inside transactions when a workflow touches multiple records or modules.
- Service methods that mutate data must check authorization at the caller boundary and enforce domain invariants internally.
- Do not hide user-facing validation errors inside generic exceptions.
- Do not return raw exception text to users.

## Module Architecture

The repository uses a first-party modular structure under `Modules/`.

Standard module folders may include:

- `config/module.php`
- `routes/web.php`
- `routes/api.php`
- `Http/Controllers`
- `Livewire`
- `resources/views`
- `resources/lang`
- `Models`
- `Services`
- `database/migrations`
- `database/seeders`
- `Imports`
- `Exports`
- `Jobs`
- `Policies`
- `Events`
- `Observers`
- `Actions`
- `DTOs`
- `Enums`
- `View/Components` or `Http/Components`

Module types:

- `shell`: presentation shell and admin composition modules, especially `Admin`.
- `support`: shared infrastructure or access modules such as `Auth`, `Role`, and `Template`.
- `domain`: business modules such as `Product`, `Order`, `Post`, `Category`, `Account`, `Admission`, `Pharma`, `Partner`, and `Website`.

Rules:

- A module owns its domain models, migrations, policies, services, and route behavior.
- `Admin` should compose and present domain features, not duplicate ownership of domain logic.
- Shared code belongs in `Modules/Shared` only when at least two modules need it and the contract is stable.
- Cross-module dependencies must be explicit in documentation and should point toward canonical domain owners.
- Never edit unrelated modules as part of a module task.

## Import/Export Architecture

- Prefer `Modules/Shared/Services/ImportExport` as the shared import/export foundation.
- Existing shared concerns include header mapping, row normalization, import reports, and export storage.
- Module-specific import/export services should define:
  - supported file types
  - header mapping
  - row normalization
  - validation rules
  - duplicate detection
  - transaction boundary
  - error report behavior
  - storage path and cleanup policy
- Large imports and exports must be chunked, lazy, or queued.
- Store temporary files privately unless a public file is explicitly required.
- Do not trust uploaded headers, file names, MIME types, row counts, or identifiers.

## Coding Standards

- Follow PSR-12 and Laravel Pint.
- Use strict, descriptive names.
- Prefer typed method signatures.
- Avoid large methods; split by business step when it improves clarity.
- Avoid global helpers unless a module already owns them and no better injection point exists.
- Keep comments short and useful. Explain non-obvious business rules, not syntax.
- Do not introduce unrelated style churn.

## Naming Conventions

- Module names use StudlyCase: `Product`, `Order`, `Admission`.
- Namespaces use `Modules\<ModuleName>\...`.
- Service classes end with `Service`.
- Livewire component classes use StudlyCase and map to kebab aliases automatically.
- Blade view names use kebab-case.
- Route names should be module-prefixed, for example `product.admin.index` or `account.users.create`.
- Permission names should be explicit capabilities, for example `system.manage`, `database.restore`, or `product.update`.
- Import and export classes end with `Import`, `Export`, or `ImportExportService` according to existing module style.

## File Generation Rules

- Read the bootstrap documents, `ROADMAP.md`, and existing module code before generating files.
- Create only files required by the requested module or documentation output.
- Preserve existing folder casing. The provider supports common lower-case and upper-case variants, but this repository mostly uses `config`, `routes`, `resources`, and `database`.
- Do not overwrite existing files without first reading them.
- Include namespace, imports, validation, authorization hooks, and tests where appropriate.
- Generated module docs go under `docs/modules/<ModuleName>/`.

## Refactoring Rules

- Refactor around a written analysis and refactor plan.
- Maintain current behavior unless the task explicitly requests a behavioral change.
- Move logic in small steps and keep the old public contract working until all callers are migrated.
- Add or update tests before risky refactors when test infrastructure is available.
- Do not rename routes, tables, columns, permissions, events, or Livewire aliases without documenting migration impact.
- Avoid broad cross-module edits during a single-module refactor.

## Safety Rules

- Treat security, authorization, data integrity, and file operations as high risk.
- Never add arbitrary command execution from HTTP or Livewire.
- Never allow browser-provided paths, table names, command names, model class names, or export destinations without server-side allowlists.
- Destructive operations require authorization, confirmation, transaction or rollback strategy, and audit logging.
- Keep secrets out of source, logs, generated docs, and process arguments.
- Validate uploads with MIME, extension, size, storage location, and row-level validation.
- Prefer private storage for generated files that contain customer, order, account, admission, or health-related data.
- Do not expose raw exceptions to users.

## Documentation Rules

- Every analyzed module should have:
  - `ANALYSIS.md`
  - `REFACTOR_PLAN.md` when refactoring is planned
  - `REBUILD_SPEC.md` when rebuilding is planned
  - `INFORMATION.md`
  - `README.md`
- Documentation must identify routes, controllers, Blade pages, Livewire components, shared UI components, services, imports, exports, shared services, models, migrations, and database tables.
- Include assumptions, risks, decisions, and verification steps.
- Keep docs current with code changes.
